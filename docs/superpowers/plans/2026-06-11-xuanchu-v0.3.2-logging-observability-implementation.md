# Xuanchu v0.3.2 日志可观测性与 MCP 反代修复实施计划

> **给 agentic workers 的要求：** 执行本计划时必须使用 `superpowers:subagent-driven-development`（如果当前环境支持子代理）或 `superpowers:executing-plans`。步骤使用 checkbox（`- [x]`）语法跟踪进度。

**目标：** 修复 `xuanchu server` 日志文件不记录常规运行信息的问题，并补齐运维可用的结构化操作日志；同时解决 HTTP MCP 在 nginx 反向代理后因 Host 头为公网域名而被 SDK localhost protection 拒绝的问题。README 中的日志配置示例、TOML 解析、server 启动日志、HTTP access log、MCP tool 调用日志、dispatcher 投递日志、scheduler 扫描日志、shutdown 日志、配置文件落盘行为和反代部署说明必须保持一致。

**状态：** 已实现并完成复审。release 文档只保留变更说明和配置示例，不展示验收清单。

**架构：** 保留现有 `internal/logging` 的 `slog` 包装与轮转实现，不引入新日志库。修复分四层：配置层兼容 README 已发布的 `[log] file = ...` 写法，同时保留 `[log.file] path = ...`；运行层把 server/access/shutdown 日志接入 `*logging.Logger`，避免继续绕过 logger 直接写 `stderr`；操作层定义稳定字段并在 HTTP、MCP、notification/hook dispatcher、reminder scheduler 的关键边界记录可追踪事件；MCP 反代层新增显式可信 Host 配置，在不关闭默认安全边界的前提下允许公网域名 Host 通过本机反代访问 `/mcp`。

**Tech Stack:** Go 1.25、`log/slog`、Cobra、`net/http`、现有 `internal/config` / `internal/logging` / `internal/cli` / `internal/httpapi`。

## 已复现问题

本计划来自 2026-06-11 的端到端检查：

- README 示例使用 `[log] file = "..."; rotate = "none"` 时，`config.parseLogConfig()` 不会创建 `Log.File`，server 启动后没有日志文件。
- 改用当前 parser 实际支持的 `[log.file] path = "..."` 后，日志文件会创建，但 `server listening`、HTTP access log、`shutdown: signal received` 都只写入 `stderr`，日志文件为空。
- 根因一：`README.md` 描述与 `internal/config/config.go:parseLogConfig()` 支持的 TOML key 不一致。
- 根因二：`internal/httpapi/middleware.go:accessLogMiddleware()` 和 `internal/cli/server.go` 的 server lifecycle 输出使用 `fmt.Fprintf(cmd.ErrOrStderr())` / `fmt.Fprintf(s.stderr)`，绕过了 `internal/logging.Logger`。
- 风险三：即使修复 access log，未来运维仍只能看到请求路径和状态，缺少 MCP tool、dispatcher delivery、scheduler rule 等后台操作记录，不足以定位“谁触发了什么、哪个投递失败、哪个规则生成了多少 delivery”。
- 线上反代问题：`github.com/modelcontextprotocol/go-sdk/mcp` v1.6.1 的 Streamable HTTP handler 默认启用 DNS rebinding protection。请求到达本机 loopback 地址时，如果 `Host` 不是 loopback/localhost，SDK 会返回 `403 Forbidden: invalid Host header "<host>"`。nginx 保留公网 Host（`proxy_set_header Host $host`）时会触发该保护；把 Host 改写为 `127.0.0.1:<port>` 虽可绕过，但会丢失真实外部 Host，不适合作为推荐部署方式。

## 日志字段契约

v0.3.2 的操作日志必须使用结构化字段，字段名保持稳定。默认 text 格式也应包含 `key=value`，json 格式应自然输出为 JSON 字段。

通用字段：

- `component`：`server`、`http`、`mcp`、`notification_dispatcher`、`hook_dispatcher`、`reminder_scheduler`
- `operation`：稳定操作名，例如 `http_request`、`mcp_tool_call`、`notification_delivery_attempt`、`hook_delivery_attempt`、`reminder_rule_scan`
- `request_id`：HTTP / HTTP MCP 请求 ID，可用时必须带上
- `method`、`path`、`status`、`duration_ms`：HTTP 请求字段
- `workspace_id`、`workspace_ref`、`project_id`、`project_ref`：可从请求或执行上下文解析时记录
- `actor_user_id`、`token_id`、`delegator_user_id`、`delegator_token_id`：认证相关字段；未认证请求用 `-`
- `impersonate_attempt`：请求携带 impersonation 但解析失败或成功时记录请求值，避免只看状态码无法判断 impersonation 参与过
- `tool`、`resource`、`mode`：MCP tool/resource 和 transport 模式字段
- `delivery_id`、`rule_id`、`hook_id`、`sink_id`、`event_type`、`object_kind`、`object_id`、`attempt`、`next_attempt_at`：投递相关字段
- `result`：`success`、`error`、`retry_wait`、`dead_lettered`、`skipped`、`draining`
- `error_code`、`error`：错误字段；`error` 可以是简短消息，不能包含 secret、token 原文或完整 request body

禁止记录：

- Bearer token 原文、admin token 原文、webhook secret、secret config value
- HTTP request / response body 原文
- HTTP template 渲染后的 Authorization header
- 用户输入中的大段自由文本全文；必要时记录 task UUID、delivery ID、rule ID 等稳定引用

Audit log 与 operation log 的边界：

- Audit log 继续记录业务审计事实，保存在数据库中，面向权限审计。
- Operation log 记录运行时可观测性，面向运维排障，不作为权限审计来源。

## MCP 反代 Host 安全契约

默认行为不变：未配置可信反代 Host 时，继续使用 MCP SDK 的 localhost protection。也就是说，`xuanchu server --listen 127.0.0.1:8080` 收到 `Host: xuanchu.example.com` 的 `/mcp` 请求时仍会拒绝。

生产反代部署使用显式 allowlist：

```toml
[server.mcp]
trusted_proxy_hosts = ["xuanchu.example.com"]
```

语义：

- 只影响 HTTP MCP `/mcp`，不影响 REST API。
- 只解决本机 loopback 后端 + 可信反代保留公网 Host 的场景。
- Host 必须精确匹配 `trusted_proxy_hosts` 中的 hostname；端口可忽略或规范化比较。
- `localhost`、`127.0.0.1`、`[::1]` 继续允许。
- 未命中 allowlist 的非 loopback Host 仍返回 403。
- 不能提供“允许所有 Host”的配置。
- 文档必须继续推荐 nginx 保留真实 Host：`proxy_set_header Host $host;`，而不是要求改写为后端 Host。

## 非目标

- 不做通用 metrics / tracing。
- 不引入 OpenTelemetry。
- 不改变 audit log 语义。
- 不改变 CLI 短命令 stdout/stderr 结果输出。
- 不记录 request body、response body、secret、token 原文。
- 不要求为每个领域 service 方法都加日志；本版本只覆盖运维排障必须的入口和后台运行时边界。
- 不提供关闭 MCP Host 防护的全局开关；只提供显式可信反代 Host allowlist。

- [x] **Step 2: deployment 手册补运维说明**

说明：

- `xuanchu server` 的 access log、启动、停机和 panic recovery 都应进入 logger。
- HTTP access log 应包含 `request_id`、`method`、`path`、`status`、`duration_ms`、actor/token/impersonation 字段。
- MCP tool/resource 日志应包含 tool/resource 名称、transport mode、workspace/project ref、result、error_code 和 duration。
- dispatcher/scheduler 日志应包含 delivery/rule/sink/object 稳定 ID、attempt、result 和简短错误。
- 未配置 log file 时，server 日志写 stderr，适合 systemd/journald 或容器 stdout/stderr 收集。
- 配置 log file 时，日志同时写 stderr 和文件；retry/replay 业务投递详情仍以 delivery 表为准。
- nginx 反代到本机 loopback 后端时，应保留真实外部 Host：

```nginx
proxy_set_header Host $host;
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

同时在 Xuanchu 配置中显式允许该外部 Host：

```toml
[server.mcp]
trusted_proxy_hosts = ["xuanchu.example.com"]
```

文档必须解释：这只影响 `/mcp` 的 SDK localhost protection，不影响 REST API 鉴权；不要把 Host 改写成 `127.0.0.1:<port>` 作为推荐做法。
