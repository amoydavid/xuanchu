# v0.4.0 Web Admin Console 与 Agent 运维入口

**日期：** 2026-06-11
**状态：** 草案
**版本：** v0.4.0
**对应 ROADMAP：** v0.3.3 之后的运维体验方向

## 1. 背景

Xuanchu 当前已经具备以下服务入口：

- 本地 CLI
- 远程 CLI client
- HTTP/JSON API server
- HTTP MCP / stdio MCP server
- Hook / notification dispatcher runtime
- SQLite / PostgreSQL 后端

这些入口都复用 `internal/app`，业务权限、workspace/project scope、Agent token、audit、delivery queue 等能力已经形成统一运行时。但日常运维仍然主要依赖 CLI、HTTP API 或 MCP tool：

- token scope、workspace allowlist、project allowlist 很难直观看懂。
- hook / notification delivery 失败后，CLI 可以查和 replay，但排障路径不够集中。
- audit log、operation log、dispatcher 状态、delivery 状态分散在多个命令和日志文件中。
- Agent token、`impersonate` scope、delegator/actor 语义对人类管理员不够可视化。
- 员工自助授权 Web UI 在 M10 中被明确排除，但它是后续 Agent 平台授权体验的自然延伸。

因此 v0.4.0 需要补一个 Web 入口。但这个入口不是 Jira / Trello / 通用任务管理前端，而是 Xuanchu server 的 **Web Admin Console**：服务管理员、Agent 平台运维者和需要排障的人类用户。

## 2. 核心判断

v0.4.0 不应把 Xuanchu 改造成多服务 Web 产品。

**硬约束：**

- 仍然只发布一个 `xuanchu` 二进制。
- `xuanchu server` 仍然是唯一常驻 server 进程。
- CLI、HTTP API、MCP、Web Console、dispatcher 必须可以由同一个二进制提供。
- Web Console 不拥有独立业务规则。
- Web Console 不直接访问 storage / GORM。
- Web Console 不通过 MCP 调用自己；它面向浏览器，MCP 面向 Agent。
- 所有可见数据和写操作继续受现有 user、membership、token scope、workspace scope、project scope、permission 检查约束。
- `CGO_ENABLED=0` 测试和构建要求不变。

## 3. 目标

v0.4.0 的目标是提供一个嵌入式 Web Admin Console，让管理员可以通过浏览器完成高价值运维与 Agent 管理工作，同时保持 Xuanchu 的单二进制发布和统一 app service 边界。

具体目标：

1. `xuanchu server` 在同一监听端口提供 `/` Web UI。
2. Console 静态资源通过 Go `embed` 打进 `xuanchu` 二进制，不要求运行时存在 Node.js、Vite dev server 或独立前端服务。
3. Console 通过现有 `/api/v1/*` 访问数据和发起写操作。
4. 缺失能力优先补通用 HTTP API，不新增长期 console-only 业务接口。
5. 第一版覆盖运维价值最高的页面：
   - 概览
   - workspace / project / member
   - PAT / Agent token
   - hook / notification sink、rule、delivery
   - audit
   - 轻量任务查询
6. 明确显示当前登录身份、token 类型、scope、workspace/project allowlist 和高风险 `impersonate` 能力。
7. 所有写操作继续写 audit；delivery replay 等运维操作继续沿用现有 audit / delivery 语义。

## 4. 非目标

v0.4.0 不做以下内容：

- 不做完整项目管理 UI。
- 不做拖拽看板。
- 不做实时协同编辑。
- 不做聊天、评论流、富文本文档。
- 不做任务多端同步协议。
- 不做外部 adapter 市场。
- 不做复杂图表 BI。
- 不做 OAuth / OIDC / SSO。
- 不做 WebSocket / SSE 实时推送。
- 不让浏览器直接访问 SQLite / PostgreSQL。
- 不让 Web Console 访问 MCP endpoint。
- 不新增一套前端专属权限模型。

任务页面只做排障和轻量查询，不替代 CLI、远程 CLI 和 Agent MCP 的主工作流。

## 5. 产品形态

### 5.1 命名

产品名称使用：

```text
Xuanchu Web Admin Console
```

文档和路线图中避免使用 `Dashboard UI` 作为正式名称。`Dashboard` 容易把范围引向报表、效率统计和项目管理看板；`Admin Console` 更符合 v0.4.0 的运维定位。

### 5.2 URL 结构

默认路由：

```text
/
/assets/*
```

现有入口保持不变：

```text
/api/v1/*
/mcp
```

`/` 是浏览器入口；`/api/v1/*` 是数据接口；`/mcp` 继续是 MCP Streamable HTTP endpoint，不放进 OpenAPI，也不被 Console 当作数据层。

### 5.3 单二进制发布

发布产物仍然是：

```text
xuanchu
```

运行方式：

```bash
xuanchu server --listen :8080
```

同一个进程同时提供：

- REST API
- HTTP MCP
- Web Console
- reminder scheduler
- notification dispatcher
- hook dispatcher
- shutdown drain
- operation log

## 6. 配置

新增配置区块：

```toml
[server.console]
enabled = true
base_path = "/"
assets_cache = "1h"
auth_mode = "bearer"
```

字段语义：

| 字段 | 默认值 | 说明 |
|---|---|---|
| `enabled` | `true` | 是否启用 Web Console 路由 |
| `base_path` | `/` | Console 挂载路径；默认发布只保证 `/`，自定义路径必须用相同 base 重新构建前端 dist |
| `assets_cache` | `1h` | 静态资源缓存时间 |
| `auth_mode` | `bearer` | v0.4.0 只实现 `bearer`，为后续 cookie session 预留 |

新增 server flag：

```bash
xuanchu server --console
xuanchu server --console=false
xuanchu server --console-base-path /admin
```

优先级沿用现有配置规则：

```text
flag > env > config file > default
```

是否需要环境变量在 implementation plan 中确定；如果添加，建议使用：

```text
XUANCHU_CONSOLE_ENABLED
XUANCHU_CONSOLE_BASE_PATH
```

`base_path` 与前端 Vite `base` 必须一致。v0.4.0 官方默认构建使用 `/`；如果部署方要把 Console 挂到 `/admin`，必须用 `VITE_XUANCHU_CONSOLE_BASE=/admin/ pnpm build` 重新生成 `internal/webconsole/dist`，再构建二进制。不能只改运行时 flag。

## 7. 认证与会话

### 7.1 v0.4.0 采用 Bearer token 模式

v0.4.0 首版只实现 Bearer token 模式：

1. 用户打开 `/`。
2. 登录页要求输入 Xuanchu token。
3. 前端把 token 保存在 `sessionStorage`。
4. 后续 API 请求携带：

```text
Authorization: Bearer <token>
```

5. 前端调用 `/api/v1/me` 验证身份，并展示当前用户、token 类型、workspace scope、project scope 和 capabilities。

选择 Bearer token 的原因：

- 复用现有 PAT / Agent token 模型。
- 不引入新的 session 表。
- 不引入 CSRF 复杂度。
- 适合 v0.4.0 的内网和管理员运维定位。

限制：

- token 只保存在当前浏览器 tab 会话级别，不默认持久化到 localStorage。
- 文档必须提醒不要在非可信设备使用 Console。
- 生产部署必须建议 TLS / 反向代理。

### 7.2 后续 cookie session 预留

后续版本可以新增 `auth_mode = "cookie"`：

```text
POST /api/v1/console/session
DELETE /api/v1/console/session
GET /api/v1/console/session
```

cookie session 需要：

- HttpOnly
- SameSite
- Secure
- CSRF token
- session 过期时间
- revoke token 后 session 失效策略

这些不进入 v0.4.0，避免首版被认证系统拖大。

## 8. 权限模型

Console 没有特殊超级权限。

有效权限仍然是：

```text
membership role 权限
∩ token capability
∩ token workspace scope
∩ token project scope
```

Console 页面按当前 token 能力动态显示操作入口：

- 没有 `token:write`：不显示创建 / revoke token 按钮。
- 没有 `hook:write`：不显示 hook delivery replay。
- 没有 `notification:write`：不显示 notification delivery replay。
- 没有 `audit:read`：隐藏 audit 页面或显示权限不足。
- project-scoped token 只显示允许 project 范围内的任务、audit、delivery。

前端隐藏按钮只是体验优化；后端仍必须完整校验权限。

### 8.1 用户信息输出

所有涉及用户身份的 API 返回继续使用 `task.UserInfo`：

```go
type UserInfo struct {
    ID          string
    Name        string
    Email       *string
    ExternalIDs []ExternalIDInfo
}
```

Console 不得要求后端新增裸 UUID 用户字段。涉及 `actor`、`delegator_user`、`created_by`、`user`、`assignees` 时，都应消费完整 `UserInfo`。

### 8.2 Impersonation 展示

Console 必须把 `impersonate` scope 视为高风险能力：

- token 列表中高亮显示带 `impersonate` 的 Agent token。
- token 创建表单中 `impersonate` 必须单独确认，不能被普通“全选”静默带上。
- audit 页面展示 actor 与 delegator 两组信息。
- Console 自身 v0.4.0 不提供“以某人身份浏览 UI”的全局切换。

## 9. 页面范围

### 9.1 登录页

功能：

- 输入 Bearer token。
- 校验 `/api/v1/me`。
- 显示登录失败原因。
- 不回显 token。
- 不把 token 写入 URL、日志或错误消息。

### 9.2 概览页

目标：让管理员 30 秒内判断 server 是否健康。

展示：

- 当前用户和 token 摘要。
- 当前 workspace。
- workspace / project 数量。
- active / pending / overdue / due soon 任务数量。
- dead-lettered hook delivery 数量。
- dead-lettered notification delivery 数量。
- 最近 10 条 audit。
- 最近失败 delivery。

如果现有 HTTP API 缺少聚合 endpoint，首版可以由前端并发调用已有 list endpoint 后聚合。只有在性能明显不合理时，才新增通用 summary API。

### 9.3 Workspace / Project / Member

功能：

- workspace list / detail。
- project list / detail。
- member list。
- member add。
- member role modify。
- project config 查看和编辑。

边界：

- 不做跨 workspace 全局搜索，除非 token 和 API 已经明确支持。
- project slug 与 project id 都要展示；脚本和 API 推荐 project id。
- project-scoped token 下，只展示允许范围内的项目和任务。

### 9.4 Token / Agent

功能：

- PAT / Agent token list。
- token detail。
- token create。
- token revoke。
- scope builder。
- workspace allowlist / project allowlist 展示。
- token raw secret 只在创建成功后显示一次。

scope builder 默认策略：

- 通用 workspace Agent token 推荐 `*` scope。
- 专用集成 token 允许选择最小 scope。
- project allowlist 作为可选收窄，而不是默认要求。
- `impersonate` 不随 `*` 的普通 UI 快捷选择自动勾选；必须二次确认。

### 9.5 Hook / Notification 运维

功能：

- notification sink list / detail。
- hook list / detail。
- notification rule / reminder rule list / detail。
- hook delivery list / detail / replay。
- notification delivery list / detail / replay。
- 按 status 过滤 delivery：

```text
queued
delivering
retry_wait
succeeded
dead_lettered
disabled_skipped
```

展示重点：

- delivery id。
- object kind / object id。
- sink name / sink type。
- status。
- attempt。
- next attempt time。
- last error。
- created / updated time。
- resolved URL 的安全展示。
- secret 不显示。
- request/response body 如现有 API 不返回，则 Console 不要求新增原文展示。

replay 语义：

- 沿用现有 replay 行为。
- replay 使用冻结请求快照，不重新渲染当前 sink 模板。
- replay 操作写 audit。

### 9.6 Audit

功能：

- audit list。
- 按 workspace、project、actor、action、时间过滤。
- 展示 actor user。
- 展示 delegator token / delegator user。
- 展示 target type / target id。
- 展示 payload 摘要。

边界：

- audit 是权限审计，不替代 operation log。
- operation log 仍在 stderr / log file。
- v0.4.0 不要求浏览器读取服务器本地日志文件。

### 9.7 轻量任务查询

功能：

- task query。
- task detail。
- due soon / overdue / assigned to me 快捷筛选。
- start / stop / done。
- annotate。

边界：

- 不做拖拽看板。
- 不做复杂甘特图。
- 不做自定义报表设计器。
- HTTP API 和 MCP 仍只接受 UUID 或 `task_slug`；纯数字 working-set ID 不进入协议契约。
- UI 可以展示 `task_slug` 和 UUID，方便复制给 Agent 或脚本。

### 9.8 主要页面 ASCII 原型

以下原型是低保真信息架构，不是最终视觉稿。实现时应保持运维工具的克制、密集、可扫描风格；不要做营销式 hero，也不要把页面做成卡片堆叠的产品首页。

## 10. HTTP API 缺口处理原则

Console 只调用 HTTP API。发现 API 缺口时按以下规则处理：

1. 如果能力已经存在于 `internal/app` 和 CLI/MCP，但 HTTP API 缺失，补通用 HTTP API。
2. 如果能力只服务 Console 排版，但不是业务能力，优先前端聚合。
3. 如果聚合数据会造成大 workspace 性能问题，再设计通用 summary endpoint。
4. 不新增长期 `/api/v1/console/*` 业务接口，除非该接口确实是 Console 会话管理或静态资源相关。

允许的 console 专属接口：

- 静态资源。
- SPA fallback。
- 未来 cookie session。

不允许的 console 专属接口：

- `consoleCreateToken` 这类绕过通用 token API 的接口。
- 直接返回未经过 app permission 的 storage 数据。
- 只为前端图表拼接而复制业务查询逻辑的接口。

### 10.1 当前可复用 HTTP API

v0.4.0 Console 的大部分页面应直接复用当前已有 HTTP API：

| Console 页面 / 能力 | 可复用 HTTP API | 说明 |
|---|---|---|
| 登录校验、当前身份 | `GET /api/v1/me` | 用于验证 Bearer token、读取 actor、token、visible workspaces 和 effective workspace |
| workspace 列表与详情 | `GET /api/v1/workspaces`、`GET /api/v1/workspaces/{workspace}` | 可用于 workspace 导航和切换 |
| workspace 修改 / 归档 | `PATCH /api/v1/workspaces/{workspace}`、`POST /api/v1/workspaces/{workspace}/archive` | 高风险操作需要前端确认 |
| member 管理 | `GET/POST /api/v1/workspaces/{workspace}/members`、`PATCH /api/v1/workspaces/{workspace}/members/{user}` | 复用现有 member role 权限 |
| project 列表与详情 | `GET /api/v1/projects`、`GET /api/v1/projects/{project}` | 展示 `project_id`、slug、状态和任务数量 |
| project 修改 / 归档 | `PATCH /api/v1/projects/{project}`、`POST /api/v1/projects/{project}/archive` | 复用 project 权限和 audit |
| project config | `GET/PUT/DELETE /api/v1/projects/{project}/config/{key}`、`GET /api/v1/projects/{project}/config` | 用于 agent context 和项目配置 |
| project annotation / timeline | `GET/POST/DELETE /api/v1/projects/{project}/annotations`、`GET /api/v1/projects/{project}/timeline` | 可用于项目详情页 |
| task query / detail | `GET /api/v1/tasks`、`GET /api/v1/tasks/{taskRef}` | `taskRef` 仍只接受 UUID 或 `task_slug` |
| task 写操作 | `POST /api/v1/tasks/{taskRef}/start`、`stop`、`done`、`annotations` | 首版轻量任务工作台直接复用 |
| user / external id | `GET/POST /api/v1/users`、`GET /api/v1/users/{user}`、`/external-ids` | 用于 member 和 assignee 选择 |
| token 列表 / 创建 / 修改 / revoke | `GET/POST /api/v1/tokens`、`PATCH/DELETE /api/v1/tokens/{tokenRef}` | raw token 只在创建响应中显示一次 |
| audit | `GET /api/v1/audit` | 已支持 limit 和 project 过滤；更多过滤见 10.2 |
| hook definition | `GET/POST /api/v1/hooks`、`GET/PATCH/DELETE /api/v1/hooks/{hookID}`、`enable/disable` | 复用现有 sink 化 Hook |
| hook delivery | `GET /api/v1/hooks/{hookID}/deliveries`、`GET /api/v1/hook-deliveries/{deliveryID}`、`POST /api/v1/hook-deliveries/{deliveryID}/replay` | 单 hook delivery 排障已可复用 |
| notification sink | `GET/POST /api/v1/notification-sinks`、`GET/PATCH/DELETE /api/v1/notification-sinks/{sinkID}`、`enable/disable` | secret 不回显 |
| reminder rule | `GET/POST /api/v1/reminder-rules`、`GET/PATCH/DELETE /api/v1/reminder-rules/{ruleID}`、`enable/disable` | 用于定时提醒管理 |
| event notification rule | `GET/POST /api/v1/notification-rules`、`GET/PATCH/DELETE /api/v1/notification-rules/{ruleID}`、`enable/disable` | 用于事件通知管理 |
| notification delivery | `GET /api/v1/notification-deliveries`、`GET /api/v1/notification-deliveries/{deliveryID}`、`POST /api/v1/notification-deliveries/{deliveryID}/replay` | 已适合 Overview 和 delivery 列表 |
| config / context | `GET/PUT/DELETE /api/v1/config/{key}`、`GET/POST/DELETE /api/v1/contexts` | 可用于 Settings 页 |

这意味着 v0.4.0 的后端主工作不是重写资源 API，而是：

- 挂载 `/` 静态资源。
- 补少量通用 HTTP API 缺口。
- 让前端以清晰方式消费现有 JSON envelope 和错误码。

### 10.2 v0.4.0 需要补的通用 API 缺口

以下缺口可以进入 v0.4.0，但必须作为通用 HTTP API 设计，不做 console-only 业务接口。

#### 10.2.1 增强 `GET /api/v1/me`

当前 `/api/v1/me` 已返回 actor、token、visible workspaces 和 effective workspace。Console 还需要展示更完整的 token 安全边界，建议增强返回：

```json
{
  "actor": {
    "id": "...",
    "name": "...",
    "email": null,
    "external_ids": []
  },
  "token": {
    "id": "...",
    "name": "...",
    "type": "agent",
    "scopes": ["*"],
    "workspace_ids": ["..."],
    "project_ids": [],
    "expires_at": null,
    "revoked_at": null
  },
  "visible_workspaces": [
    {"id": "...", "slug": "..."}
  ],
  "effective_workspace": {"id": "...", "slug": "..."}
}
```

要求：

- `actor` 使用完整 `task.UserInfo` JSON。
- token 不返回 raw secret 或 token hash。
- `workspace_ids` / `project_ids` 反映 token allowlist；空 project list 表示不按 project 收窄。
- 保持旧字段兼容，避免破坏远程 CLI。

#### 10.2.2 新增 `GET /api/v1/scopes`

Token scope builder 需要稳定的 capability 列表。新增：

```text
GET /api/v1/scopes
```

返回示例：

```json
{
  "data": [
    {
      "name": "task:read",
      "category": "task",
      "risk": "normal",
      "description": "Read tasks"
    },
    {
      "name": "impersonate",
      "category": "auth",
      "risk": "high",
      "description": "Act as another workspace member when allowed"
    }
  ]
}
```

要求：

- 复用现有 scope 定义，不能在前端硬编码第二套权限定名。
- `impersonate` 标记为高风险。
- `*` 作为合法通配符暴露，并说明不会绕过 membership、workspace allowlist、project allowlist。

#### 10.2.3 新增全局 Hook Delivery 列表

当前已有：

```text
GET /api/v1/hooks/{hookID}/deliveries
GET /api/v1/hook-deliveries/{deliveryID}
POST /api/v1/hook-deliveries/{deliveryID}/replay
```

Overview 需要查看最近失败 hook delivery，不应要求前端先列出所有 hook 再逐个查询。新增：

```text
GET /api/v1/hook-deliveries?status=&limit=&project=&project_id=
```

要求：

- 复用 `hook:read` 和 `PermissionHookRead`。
- status 支持当前真实状态：`queued`、`delivering`、`retry_wait`、`succeeded`、`dead_lettered`、`disabled_skipped`。
- project-scoped token 只能看到 allowlist 内的 delivery。
- 返回结构与单条 `hook-deliveries/{deliveryID}` 保持一致。

#### 10.2.4 增强 Audit 过滤

当前 `GET /api/v1/audit` 支持 `limit`、`project`、`project_id`。Console 过滤需要逐步增强：

```text
GET /api/v1/audit?project=&project_id=&actor=&action=&since=&until=&limit=
```

要求：

- `actor` 接受 user name、email 或 UUID。
- `action` 精确匹配 audit action。
- `since` / `until` 使用 Unix 秒或后端现有日期解析规则；implementation plan 固定一种。
- 不改变 audit 写入语义。
- 不把 operation log 混进 audit。

### 10.3 Overview 聚合策略

Overview 首版优先前端聚合：

- `GET /api/v1/me`
- `GET /api/v1/workspaces`
- `GET /api/v1/projects`
- `GET /api/v1/tasks?query=...&limit=...`
- `GET /api/v1/audit?limit=10`
- `GET /api/v1/hook-deliveries?status=dead_lettered&limit=10`
- `GET /api/v1/notification-deliveries?status=dead_lettered&limit=10`

只有在大 workspace 下证明前端聚合慢或请求数过多时，才新增通用 summary endpoint。summary endpoint 必须服务 HTTP API / 远程 CLI / Console 的共同需求，不应只服务图表。

建议新增目录：

```text
web
```

### 12.1 开发态与打包态契约

v0.4.0 固定以下目录：

```text
web                         # React + Vite + shadcn/ui 源码
internal/webconsole/dist    # Go embed 使用的最终静态资源
```

开发态：

```bash
xuanchu server --listen :8080
cd web
pnpm dev
```

Vite dev server 默认监听 `5173`，浏览器访问：

```text
http://localhost:5173/
```

前端代码只请求同源 `/api/v1/*`。开发态由 Vite proxy 把 `/api/v1/*` 转发到 `http://127.0.0.1:8080`，目标地址可用 `VITE_XUANCHU_API_TARGET` 覆盖。Console 不代理也不调用 `/mcp`。默认开发和发布 base 都是 `/`；自定义 base 必须同时设置 `VITE_XUANCHU_CONSOLE_BASE` 和 Go server `console.base_path`。

打包态：

```bash
cd web
pnpm build
```

Vite build 必须直接输出到：

```text
../internal/webconsole/dist
```

`xuanchu server` 生产运行时从同一二进制内嵌的 `internal/webconsole/dist` 提供 `/`、`/assets/*` 和 SPA fallback。生产态前端仍请求同源 `/api/v1/*`，不需要单独前端服务。

关于构建产物有两种可选方案，implementation plan 必须固定一种：

### 12.2 方案 A：提交前端 dist

把 `internal/webconsole/dist` 提交到仓库。`web` 保留唯一前端应用源码和构建配置，Vite build 直接输出到 Go embed 使用的 dist 目录。

优点：

- `go build ./cmd/xuanchu` 不需要 Node.js。
- 最符合当前 Go 项目简单构建体验。

缺点：

- 仓库会出现生成产物。
- 前端源码和 dist 可能漂移，需要 CI 检查。

### 12.3 方案 B：空壳 fallback + release 构建注入

源码中保留一个最小 fallback `index.html`，发布流程先跑前端 build，再注入正式 dist。

优点：

- 避免提交大量 dist。
- 前端源码是唯一真实来源。

缺点：

- 普通 `go build` 得到的是空壳 Console。
- 容易和“一个二进制可访问所有服务”的预期冲突。

推荐 v0.4.0 采用 **方案 A**。原因是 Xuanchu 当前最重要的工程约束是单二进制和 `CGO_ENABLED=0 go build` 可信；提交 dist 虽然不优雅，但能减少部署和构建歧义。

### 13.1 中英文 i18n

Console v0.4.0 必须支持中文和英文界面：

- 默认语言为 `zh-CN`。
- 支持 `en-US`。
- 首次进入可按浏览器语言选择；不匹配时回退到 `zh-CN`。
- 已登录页面顶部提供语言切换。
- 语言偏好可以保存在 `localStorage`，但 token 仍然只能保存在 `sessionStorage`。
- 导航、页面标题、按钮、表单 label、确认文案、空状态、错误提示、权限提示、风险提示都必须走 i18n 资源。
- 后端返回的用户数据、任务标题、项目名称、audit action、delivery status 等业务数据不翻译，只翻译 UI label 和解释文案。
- 后端 error `code` 在前端映射为本地化文案；原始 `message` 可以作为调试细节展示，但不能泄露 token 或 secret。

实现建议使用 `i18next` + `react-i18next`，翻译资源放在：

```text
web/src/locales/zh-CN.ts
web/src/locales/en-US.ts
```

组件中不得直接硬编码中英文 UI 文案。ASCII 原型只表达信息架构，不代表最终语言资源。

### 13.2 视觉风格与 light/dark

Console v0.4.0 采用接近 Vercel 的运维控制台风格：

- 中性黑白灰为主，使用少量语义色表达成功、警告、危险、信息。
- 细边框、低饱和背景、清晰 hover/focus 状态。
- 信息密度偏高，但通过分组、间距、表格列、标题层级保证可扫描。
- 不做营销式 hero、渐变大背景、装饰性插画、卡片堆叠首页。
- 字体使用系统 sans-serif 栈，优先保证跨平台清晰和控制台工具感。
- 页面标题、说明文字、工具栏、筛选器、表格、详情区形成明确层级；不能把所有信息都放成同等权重的卡片。

控件使用原则：

- 导航使用侧边栏和 active state，不用 tab 伪装全局导航。
- 资源列表使用 `Table`，配合 `Badge` 展示 status / risk / scope。
- 筛选使用 `Input`、`Select`、`Combobox`、`Date/Time` 输入，不用自由文本替代结构化选项。
- 二元设置使用 `Switch` 或 `Checkbox`。
- 高风险操作使用 `Dialog` / `AlertDialog` 二次确认。
- 页面内视图切换使用 `Tabs`，批量或行内操作使用 `DropdownMenu`。
- 图标按钮必须有 `Tooltip` 和可访问 label。
- 复制 UUID、token prefix、task_slug 等使用明确的 copy button。

light/dark 模式是首版基础能力：

- 默认跟随系统主题。
- 用户可以在顶部切换 `light` / `dark` / `system`。
- 主题偏好可以保存在 `localStorage`；token 仍然只能保存在 `sessionStorage`。
- 使用 shadcn/ui CSS variables 和 Tailwind `dark` class，不维护两套样式。
- 所有页面、Dialog、Dropdown、Tooltip、Table hover、focus ring、Badge 语义色都必须在 light/dark 下可读。
- Playwright smoke 至少覆盖 light 和 dark 两种主题下的登录页和 Overview。

## 14. 错误处理

Console 必须统一处理以下错误：

| HTTP / code | UI 行为 |
|---|---|
| 401 | 清除 token 并回到登录页 |
| 403 / permission denied | 页面内显示权限不足 |
| 404 / task_not_found / project_not_found | 显示资源不存在或不可见，不泄露越权资源存在性 |
| token_scope_denied | 明确提示 token scope 不足 |
| workspace_required | 要求用户选择 workspace |
| project_scope_denied | 提示 project allowlist 限制 |
| validation error | 表单字段级错误 |
| server error | 显示 request id，如后端返回 |

前端不应把错误吞掉，也不应把 token、secret、webhook body、Authorization header 放进错误提示。

## 15. 安全要求

### 15.1 Token 安全

- token 不进入 URL。
- token 不写 localStorage。
- token 不打印到 console log。
- token 不进入 operation log。
- token raw secret 只在创建时显示一次。
- logout 清空 sessionStorage。

### 15.2 Secret 安全

Console 不显示：

- webhook secret。
- HTTP template secret 原文。
- Authorization header 渲染结果。
- Bearer token。
- 数据库连接串密码。

如需确认 secret 轮换，只显示不可逆 fingerprint 或后端已有安全摘要。

### 15.3 静态资源安全

- `/assets/*` 可以缓存。
- `/index.html` 不应长期强缓存。
- SPA fallback 只对 console base path 生效，不能吞掉 `/api/v1/*` 或 `/mcp`。
- 生产部署文档继续建议 TLS termination。

### 15.4 SSRF / 出站投递

Console 不能绕过已有 sink endpoint 安全策略。新增 sink 或修改 endpoint 仍然必须经过后端 allowed host / SSRF 校验。

## 16. 可观测性

Console 自身请求进入现有 HTTP access log。

需要记录：

- path
- method
- status
- request id
- actor user id
- token id
- duration

不能记录：

- Bearer token
- webhook secret
- request body 中的 secret
- rendered Authorization header

Console 静态资源请求可以降低日志噪音；是否记录由现有 access log 策略决定。

```bash
git diff --exit-code -- internal/webconsole/dist
```

v0.4.0 固定使用 `internal/webconsole/dist` 作为 dist 路径；如果未来调整路径，必须同步更新 Go embed、前端 Vite 配置和 drift check。

## 19. 与现有能力的关系

### 19.1 CLI

CLI 仍然是一等入口。Console 不替代 CLI：

- 批量脚本继续用 CLI / HTTP API。
- 本地数据库操作继续用本地 CLI。
- 工作集数字 ID 继续是 CLI 交互体验。

### 19.2 HTTP API

HTTP API 是 Console 的数据层。任何 Console 需要的业务能力，优先沉淀为通用 HTTP API。

### 19.3 MCP

MCP 仍然面向 Agent。Console 不调用 MCP，也不改变 MCP tool 命名、schema 或 resource 语义。

### 19.4 Dispatcher

Console 只观察和触发已有 delivery 管理能力，不改变 dispatcher 队列语义：

- DB delivery 表仍是可靠队列。
- 进程内 worker 仍只做短暂执行协调。
- replay 仍使用冻结快照。
- dispatcher 状态推进仍由 server runtime 完成。

## 20. 兼容性

- 默认 server 启动路径新增 `/`，不影响已有 `/api/v1` 和 `/mcp`。
- 禁用 Console 后应表现为路由不存在。
- HTTP API JSON schema 不应为 Console 破坏兼容。
- OpenAPI 只描述 `/api/v1/*`，不描述 `/mcp`，是否描述 console session endpoint 等到 cookie session 阶段再定。
- 前端构建依赖不进入 Go runtime。

## 21. 风险与决策

### 21.1 提交 dist 的取舍

提交 dist 会带来生成产物漂移风险，但它最符合当前单二进制和普通 `go build` 体验。v0.4.0 推荐提交 dist，并用 drift check 控制一致性。

### 21.2 Bearer token 登录的安全边界

Bearer token 模式简单，但不如 HttpOnly cookie session。v0.4.0 接受这个取舍，因为目标是内网和管理员运维入口。文档必须把 TLS 和可信设备写清楚。

### 21.3 页面范围膨胀

任务页面最容易膨胀成项目管理产品。v0.4.0 必须把任务页面限定为轻量查询和排障操作，不做看板。

### 21.4 API 聚合性能

Overview 如果完全前端聚合，未来大 workspace 可能慢。v0.4.0 可以先前端聚合；如实测慢，再补通用 summary API，不能提前造一套只服务图表的后端。

## 22. 验收标准

v0.4.0 完成时必须满足：

1. `xuanchu` 仍然是唯一发布二进制。
2. `xuanchu server --listen :8080` 后可以访问 `/`、`/api/v1/*`、`/mcp`。
3. Console 不要求运行时 Node.js。
4. Console 所有业务请求走 HTTP API。
5. Console 不直接访问 storage。
6. Console 不调用 MCP。
7. token、secret、Authorization header 不被前端或后端日志泄露。
8. project-scoped token 在 Console 中不能越权查看其他 project。
9. delivery replay、token revoke、member role modify 等写操作仍写 audit。
10. `go test ./...` 通过。
11. `CGO_ENABLED=0 go test ./...` 通过。
12. `CGO_ENABLED=0 go build ./cmd/xuanchu` 通过。
13. 前端 typecheck / build 通过。
14. 文档说明单二进制部署、Console 登录、安全边界和不进入范围的任务看板能力。

## 23. 后续可能方向

v0.4.0 之后可以单独规划：

- cookie session。
- 员工自助授权 Agent 平台。
- 只读 operation log viewer。
- 大 workspace summary API。
- adapter 管理页面。
- 更完整的任务工作台。
- WebSocket / SSE 实时状态。
- SSO / OIDC。

这些都不进入 v0.4.0 首版，避免破坏当前“运维入口”的清晰边界。
