# v0.1.0 设计文档：配置文件指定、通用日志框架、全层 panic recovery、版本号自动化

日期：2026-06-05

## 1. 背景

taskg 经历 M0–M15 的快速迭代，已具备完整的 CLI、HTTP API、MCP Server、Remote Client 能力。现在需要补齐运维和可观测性的基础设施，使其达到可正式发布（v0.1.0）的质量标准。

当前存在的三个缺口：

1. 配置文件路径硬编码为 `$XDG_CONFIG_HOME/taskg/taskg.toml` 或 `~/.config/taskg/taskg.toml`，不支持 `--config` 指定路径，部署时无法灵活切换配置。
2. 只有 HTTP 层有 panic recovery（`recovererMiddleware`），CLI 和 MCP 层 panic 直接崩溃，无法记录现场。
3. 版本号通过 ldflags 注入，`go install` 或裸 `go build` 只显示 `dev`，无法追溯构建来源。

此外，panic recovery 需要日志文件支持，而当前项目没有结构化日志框架。因此一并引入通用日志框架，为后续 hook 调度日志、HTTP 访问日志等扩展打基础。

## 2. 目标

- 支持 `--config` / `TASKG_CONFIG` 指定 TOML 配置文件路径。
- 引入基于 `log/slog` 的通用日志框架，支持文件输出、轮转、级别过滤。
- CLI、HTTP、MCP 三层全部覆盖 panic recovery，panic 时记录堆栈到日志文件。
- 版本号从 `debug.ReadBuildInfo()` 自动读取 git 信息，ldflags 仅用于正式发布覆盖。

## 3. 非目标

- 不引入外部日志库（zap、zerolog 等），使用 Go 标准库 `log/slog`。
- 不实现日志远程上报（syslog、Loki 等）。
- 不改变现有 TOML 配置的已有字段语义。
- 不实现 log compaction 或压缩归档。

## 4. 特性 1：`--config` 指定 TOML 文件路径

### 4.1 接口

- CLI flag：`--config /path/to/config.toml`
- 环境变量：`TASKG_CONFIG=/path/to/config.toml`
- 两者等价，CLI flag 优先于环境变量。

### 4.2 优先级链

配置值的解析优先级（高 → 低）：

1. CLI flags（`--db`、`--db-url` 等）
2. 环境变量（`TASKG_DB`、`TASKG_DB_URL` 等）
3. `--config` / `TASKG_CONFIG` 指定的 TOML 文件
4. XDG 默认路径的 TOML 文件（`~/.config/taskg/taskg.toml`）
5. 内置默认值

注意：`--config` 只控制从哪个文件加载配置，不参与配置值本身的优先级链。

当 `--config` 指定的文件不存在时，报错退出。不静默回退到 XDG 默认路径。

### 4.3 实现要点

- `config.Options` 新增 `ConfigPath string` 字段。
- `config.Resolve` 中，当 `ConfigPath` 非空时直接调用 `loadTomlConfigFile(ConfigPath)`，跳过 `findTomlConfigPath` 的目录搜索逻辑。
- `cli.Options` 新增 `Config string` 字段。
- `NewRootCommand` 注册 `cmd.PersistentFlags().StringVar(&opts.Config, "config", opts.Config, "TOML 配置文件路径")`。
- `splitFlagsRcAndPositional` 的 `stringFlags` 注册 `"--config": true`。
- `buildServiceFromOpts` 将 `opts.Config` 传入 `config.Options.ConfigPath`。
- `cmd/taskg/main.go` 的 `warningOptionsFromArgs` 解析 `--config` 参数。
- `RuntimeEnv()` 增加 `TASKG_CONFIG`。

### 4.4 测试

- `config_test.go`：`ConfigPath` 指定文件存在时正常加载；指定文件不存在时返回错误。
- `cli_test.go`：`--config` flag 正确传递到配置解析。
- 集成测试：`--config /nonexistent` 返回错误退出。

## 5. 特性 2：通用日志框架

### 5.1 包结构

新增 `internal/logging` 包，提供：

```go
package logging

type LogConfig struct {
    Level  string       `toml:"level"`  // debug | info | warn | error，默认 info
    Format string       `toml:"format"` // text | json，默认 text
    File   *FileConfig  `toml:"file"`
}

type FileConfig struct {
    Path       string `toml:"path"`         // 日志文件路径，支持 ~ 展开
    Rotate     string `toml:"rotate"`       // daily | size | none，默认 none
    MaxSizeMB  int    `toml:"max_size_mb"`  // rotate=size 时生效，默认 100
    MaxAgeDays int    `toml:"max_age_days"` // 保留天数，0=不清理
}

func Setup(cfg LogConfig, stderr io.Writer) (*Logger, func() error, error)
```

### 5.2 TOML 配置格式

```toml
[log]
level = "info"
format = "text"

[log.file]
path = "~/.local/share/taskg/logs/taskg.log"
rotate = "daily"
max_age_days = 30
```

### 5.3 Logger 设计

```go
type Logger struct {
    inner *slog.Logger
    file  *os.File  // 日志文件句柄，nil 表示仅 stderr
    mu    sync.Mutex // 保护文件轮转时的写入
}

func (l *Logger) Debug(msg string, args ...any)
func (l *Logger) Info(msg string, args ...any)
func (l *Logger) Warn(msg string, args ...any)
func (l *Logger) Error(msg string, args ...any)

func (l *Logger) With(args ...any) *Logger
```

`Setup` 返回的 `func() error` 是清理函数，负责关闭文件句柄、flush 缓冲区。调用方应 `defer closeFn()`。

### 5.4 环境变量覆盖

- `TASKG_LOG_LEVEL`：覆盖 `log.level`
- `TASKG_LOG_FILE`：覆盖 `log.file.path`

环境变量优先于 TOML 文件配置。`TASKG_LOG_LEVEL` 接收非法值时静默降级为默认级别 `info`。

### 5.5 轮转策略

| 策略 | 行为 |
|------|------|
| `none` | 单文件追加写入 |
| `daily` | 文件名带日期后缀 `taskg-2026-06-05.log`。每次写入前检查当前日期是否与文件日期一致，不一致则关闭旧句柄、打开新文件。不依赖定时器。 |
| `size` | 当前文件达到 `max_size_mb` 时重命名为 `taskg.log.1`、`taskg.log.2`...，最多保留 5 个历史文件（硬编码 `const maxBackups = 5`，v0.1.0 不暴露为配置项） |

`max_age_days`：启动时扫描日志目录，删除修改时间超过 N 天的旧日志文件。0 表示不清理。

### 5.6 CLI 模式 vs Server 模式

- **CLI 模式**（本地命令）：默认不写日志文件（仅配置了 `[log.file]` 才写），运行时间短，不需要常驻日志。
- **Server 模式**（`taskg server` / `taskg mcp`）：配置了 `[log.file]` 则写文件，否则写 stderr。

### 5.7 配置解析集成

- `config.Config` 新增 `Log logging.LogConfig` 字段。
- TOML 加载时解析 `[log]` 区块到 `LogConfig`。
- 现有的 `flattenTomlMap` 机制已支持嵌套 key（`log.level`、`log.file.path`），无需改动。

### 5.8 消费者

v0.1.0 的日志消费者：

| 消费者 | 级别 | 说明 |
|--------|------|------|
| panic recovery | Error | panic 值 + 完整堆栈 |
| HTTP recovererMiddleware | Error | 同上 |
| MCP tool panic | Error | 同上 |

v0.1.0 不迁移现有 `accessLogMiddleware` 的 stderr 写入，后续版本再将其接入 Logger。

后续可扩展：hook 调度日志、MCP tool 调用日志、数据库操作慢日志等。

### 5.9 初始化时序

Logger 的创建位置和传递路径：

| 入口 | Setup 调用位置 | Logger 传递 |
|------|---------------|-------------|
| CLI 短命令 | `buildServiceFromOpts`（`cli/root.go`） | 写入 `config.Config.Log`，由调用方创建 Logger 并存入 Options |
| `taskg server` | `cli/server.go` 的 server 启动前 | 写入 `httpapi.Options.Logger`，传入 `Server` 结构体 |
| `taskg mcp` (stdio) | `cli/mcp.go` 的 MCP 启动前 | 写入 `mcpserver.Options.Logger`，`RegisterAllTools` 时设为包级变量 |
| `taskg mcp` (HTTP) | 同 `taskg server`，走 HTTP 中间件 | `httpapi.Options.Logger` |

全局流程：`config.Resolve` → 解析 `[log]` → `logging.Setup(cfg.Log)` → 将 Logger 注入各模块 Options。

### 5.10 测试

- `logging_test.go`：各级别过滤、文件输出、路径展开、轮转切换、`Setup()` 全零值降级、Level 非法值降级。
- 集成测试：TOML 配置 `[log]` 区块正确生效。

## 6. 特性 3：全层 panic recovery

### 6.1 CLI 层

在 `cmd/taskg/main.go` 的 `main()` 函数中：

```go
func main() {
    defer handlePanic()
    // ... 现有逻辑
}

func handlePanic() {
    if r := recover(); r != nil {
        fmt.Fprintln(os.Stderr, "taskg: internal error")
        // 初始化最小化 logger（不依赖完整配置），写入 panic 日志
        logPanic(r)
        os.Exit(1)
    }
}
```

`logPanic` 的策略：
- 尝试通过 `internal/logging` 的 Logger 写入（如果已初始化）。
- 如果 Logger 未初始化（配置解析前的早期 panic），直接写入默认路径 `~/.local/share/taskg/logs/panic.log`（硬编码，不依赖 config 解析，即使 `--data-dir` 指定了其他目录也不受影响——这是有意为之的最后兜底）。
- 目录不存在时自动创建（`os.MkdirAll`，权限 0755）。
- 创建目录或文件失败时，将 panic 信息同时写入 stderr 作为最后兜底。
- `logPanic` 自身用 `defer recover()` 保护，防止日志写入过程中再次 panic 导致无限递归。
- 日志内容：时间戳 + panic 值 + `debug.Stack()` 完整堆栈。

### 6.2 HTTP 层

已有 `recovererMiddleware`（`internal/httpapi/middleware.go:43`），改动：

- panic 恢复后，除了返回 500 响应，同时通过 Logger 写入 Error 级别日志。
- Logger 从 `Server` 结构体获取（`Server` 持有 `*logging.Logger`）。

### 6.3 MCP stdio 层

在 `internal/mcpserver/tools_common.go` 的 `addTool` 函数中，在 `s.AddTool` 的闭包内统一加 `defer recover()`。这是所有 MCP tool handler 的唯一入口，改动最小且覆盖完整：

```go
s.AddTool(tool, func(ctx context.Context, req *mcp.CallToolRequest) (*mcp.CallToolResult, error) {
    defer func() {
        if r := recover(); r != nil {
            mcpLogger.Error("panic in tool", "tool", tool.Name, "panic", r, "stack", string(debug.Stack()))
            // 返回错误 envelope
        }
    }()
    var input In
    // ... 现有逻辑（json.Unmarshal、handler 调用等）
})
```

Logger 传递方式：使用包级变量 `var mcpLogger *logging.Logger`，在 `mcpserver.RegisterAllTools(opts)` 入口处从 `opts.Logger` 设置。`addTool` 不改签名，直接引用包级变量。这样不影响 70+ 调用点。

MCP 层 panic 时：
- 返回 `ToolEnvelope{Success: false, Error: "internal error"}` JSON。
- 通过 Logger 写入 Error 级别日志（含堆栈）。
- 不退出进程。

### 6.4 MCP HTTP 层

MCP HTTP 请求走 `httpapi.Server` 的 `recovererMiddleware`，已覆盖。需确保 MCP handler 的 panic 能被外层 middleware 捕获。

### 6.5 测试

- `main_test.go`：模拟 panic，验证 stderr 输出和日志文件写入。
- `server_test.go`：已有 `TestPanicIsRecoveredAsErrorEnvelope`，验证 Logger 同时写入。
- MCP 集成测试：tool handler 内 panic 时返回错误 envelope 而非断开连接。

## 7. 特性 4：版本号自动化

### 7.1 当前状态

- `var version = "dev"`（`cmd/taskg/main.go:17`）
- Makefile 通过 ldflags 注入：`CGO_ENABLED=0 go build -o taskg ./cmd/taskg`

### 7.2 改动

```go
var version = "" // ldflags 覆盖

func resolveVersion() string {
    if version != "" {
        return version
    }
    info, ok := debug.ReadBuildInfo()
    if !ok {
        return "dev"
    }
    var rev, t string
    for _, s := range info.Settings {
        switch s.Key {
        case "vcs.revision":
            rev = s.Value
        case "vcs.time":
            t = s.Value
        }
    }
    if rev == "" {
        return "dev"
    }
    short := rev
    if len(short) > 12 {
        short = short[:12]
    }
    v := "dev+" + short
    if t != "" {
        if pt, err := time.Parse(time.RFC3339, t); err == nil {
            v += " " + pt.Format("2006-01-02")
        }
    }
    return v
}
```

注意：dev 版本前缀从 `"0.1.0-dev+"` 简化为 `"dev+"`，避免每次发版手动修改代码。正式版本始终通过 `git tag` + ldflags 注入（如 `v0.1.0`），dev 前缀只出现在未打 tag 的构建中。

### 7.3 输出格式

| 场景 | 命令 | 输出 |
|------|------|------|
| 正式发布 | `go build -ldflags "-X main.version=0.1.0"` | `taskg 0.1.0` |
| 开发构建 | `go build ./cmd/taskg` | `taskg dev+abc1234def5 2026-06-05` |
| go install | `go install ./cmd/taskg` | `taskg dev+abc1234def5 2026-06-05` |
| 无 git 信息 | 非 git 目录构建 | `taskg dev` |

### 7.4 Makefile 更新

```makefile
VERSION ?= $(shell git describe --tags --exact-match 2>/dev/null || echo "")
BINARY := taskg
CMD := ./cmd/taskg

build:
	$(if $(VERSION),\
		CGO_ENABLED=0 go build -ldflags "-X main.version=$(VERSION)" -o $(BINARY) $(CMD),\
		CGO_ENABLED=0 go build -o $(BINARY) $(CMD))
```

- `make build`：自动检测 git tag，有 tag 则用 tag 作为版本号，否则交给 `resolveVersion()` 自动推断。
- `make build VERSION=0.2.0`：手动指定版本号。

### 7.5 测试

- 单元测试：`resolveVersion()` 各分支。
- 集成测试：`taskg --version` 输出包含版本信息。

## 10. 里程碑定义

完成以上四个特性 + 全量测试通过，即标记为 v0.1.0。

发布流程：
1. 确保所有测试通过（`go test ./...` + `CGO_ENABLED=0 go build ./cmd/taskg`）。
2. 更新 README.md 和 ROADMAP.md。
3. `git tag v0.1.0`。
4. `make build`（自动用 tag 作为版本号）。
5. 部署到生产环境。

## 11. 向后兼容

- `--config` 是新增 flag，不影响现有用法。
- `[log]` 是新增 TOML 区块，不存在时使用默认值（不写日志文件）。
- panic recovery 不改变正常流程行为，只在异常时生效。
- `resolveVersion()` 是 `version` 变量的内部增强，ldflags 覆盖方式不变。

## 12. 风险

- `debug.ReadBuildInfo()` 在 `go install` 时 `vcs.*` 信息可能为空（取决于 Go 版本和构建方式），需测试覆盖。
- 日志轮转在 Windows 上的文件锁行为可能不同，当前项目主要在 macOS/Linux 上运行，暂不特殊处理。
- `daily` 轮转需要进程持续运行才能检测日期切换。对于短命 CLI 命令，每次启动检查当前日期对应的文件即可。
