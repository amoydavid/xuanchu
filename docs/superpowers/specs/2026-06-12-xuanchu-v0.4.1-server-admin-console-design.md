# v0.4.1 Server Admin Console、Workspace 管理与 Bootstrap

**日期：** 2026-06-12
**状态：** 草案
**版本：** v0.4.1
**对应 ROADMAP：** v0.4.0 Web Admin Console 后续增强

## 1. 背景

v0.4.0 已经引入嵌入式 Web Admin Console，并把浏览器入口放在 `/`。普通 Console 使用 PAT / Agent token 登录，后续请求走 `/api/v1/*`，继续受 workspace membership、token scope、workspace allowlist 和 project allowlist 约束。

同时，Xuanchu 已经具备 server admin bootstrap 能力：

- `xuanchu admin token generate` 生成 server admin token 明文和 hash。
- `[server.admin]` 通过 hash 或 hash_env 配置 admin verifier。
- `/api/v1/admin/workspaces` 可以创建 workspace 和初始 owner。
- `/api/v1/admin/workspaces/{workspace}/agent-tokens` 可以为 workspace 创建 Agent token。

当前缺口有三个：

1. 这套 bootstrap 能力只能通过 curl / 自动化平台调用，浏览器 Console 还不能以 server admin 身份完成“创建 workspace、创建 workspace 管理员、创建管理员 Agent token”的初始化闭环。
2. admin token verifier 主要依赖配置文件，新增或轮换 token 需要改配置并重启服务；这不适合长期运行的单二进制 server。
3. server admin 登录后没有持续的 workspace 管理入口，也不能从 `/admin/*` 安全地切换到某个 workspace 的管理员视角处理成员、token、配置等已有普通 Console 能力。

v0.4.1 的目标是补齐这个控制面 UI，并把 server admin token verifier 从“配置文件为主”调整为“数据库持久化为主”。配置文件只负责启用或关闭 server admin 控制面；无有效 admin token 时，server 通过控制台一次性 setup-code 引导 `/admin/setup` 生成第一个 admin token。server admin 登录后应能管理 workspace 控制面资源，并通过短期 acting session 进入任意 workspace 的管理员视角，完成后退回 `/admin/*`。

## 2. 核心判断

### 2.1 server admin 不是普通用户超管

server admin token 是 server control-plane bootstrap token，不是 PAT，不是 Agent token，不写入普通 `api_tokens` 表，也不拥有普通业务 scope。

v0.4.1 新增独立 `server_admin_tokens` verifier 表。该表只保存 admin token 的 hash、prefix、名称和状态，不保存 raw token。admin token 仍只能用于 `/api/v1/admin/*`。

它只能访问 `/api/v1/admin/*` 下明确暴露的控制面接口，不能访问：

- `/api/v1/tasks`
- `/api/v1/projects`
- `/api/v1/workspaces`
- `/api/v1/tokens`
- `/api/v1/hooks`
- `/api/v1/notification-*`
- `/mcp`

普通 PAT / Agent token 也不能访问 `/api/v1/admin/*`。

### 2.2 不做登录页模式切换

普通登录和 server admin 登录必须是两个入口：

```text
/              普通 Web Console 登录入口，输入 PAT / Agent token
/admin/login   Server Admin 登录入口，输入 xuanchu_admin_...
/admin/setup   首次初始化入口，输入控制台 setup-code 后生成第一个 admin token
/admin         Server Admin Console 首页
```

`/` 可以提供一个低调链接跳到 `/admin/login`，但不能在同一个表单中提供“模式切换”。

原因：

- 两种 token 的权限语义完全不同。
- 模式切换会让用户误以为 admin token 是普通 token 的高权限形态。
- 分离 URL 可以让浏览器历史、书签、测试和审计语义更清楚。

### 2.3 视觉上必须明显区分

普通登录页继续保持 v0.4.0 的干净 Console 风格。

`/admin/login` 必须呈现控制面语义：

- 明确标题：`Server Admin Control Plane`
- 明确说明：只用于管理 workspace 控制面、workspace 管理员、Agent token 和短期管理员视角切换。
- 显示高风险标识：`High risk`
- 不显示普通 workspace 上下文。
- 成功登录后 admin 区域顶部持续显示 `Server Admin · <token_name>`。

视觉差异不是装饰，而是权限边界提示。

### 2.5 admin verifier 以数据库为准

`[server.admin]` 仍作为控制面总开关：

```toml
[server.admin]
enabled = true
```

但 v0.4.1 不再要求管理员把长期 admin token hash 写进配置文件。server 启动后读取数据库中的 `server_admin_tokens`：

- 存在至少一个 `enabled=true` 且未 revoked 的 token：`/admin/login` 正常工作。
- 完全没有有效 token：server 进入 setup mode，控制台输出一次性 setup-code；`/admin/login` 提示进入 `/admin/setup`。
- `enabled=false`：不挂载 admin 控制面，`/api/v1/admin/*` 返回 `route_not_found`。

旧的 `[[server.admin.tokens]]` / `hash_env` 作为兼容 verifier 保留一个版本，但文档标记为 deprecated。后续应提供迁移命令把配置 hash 导入 `server_admin_tokens` 后删除配置项。

### 2.6 setup-code 不是 admin token

setup-code 只用于首次初始化，不是长期凭证：

- server 启动时仅在“无有效 admin token”情况下生成。
- 只保存在进程内存，不落库，不进入 audit。
- 只输出到 server 控制台 / stderr，不通过 API 返回。
- 有 TTL，默认 30 分钟。
- 只能成功使用一次；生成 admin token 后立即失效。
- setup-code 只允许调用 `POST /api/v1/admin/setup`，不能访问其它 admin endpoint。

`/admin/setup` 成功后，服务端生成 raw `xuanchu_admin_...`，把 `sha256:<hex>` 写入 `server_admin_tokens`，并只在响应中返回一次 raw token。之后管理员用该 token 登录 `/admin/login`，不需要重启服务。

### 2.7 server admin 可以管理 workspace 控制面，但不直接读写业务数据

server admin 的职责是管控 server 和 workspace 控制面资源：

- 列出所有 workspace，包括已归档 workspace。
- 查看 workspace 的 owner/admin/member 摘要、token 摘要和审计入口。
- 创建 workspace、创建或提升 workspace owner/admin、创建 workspace-scoped Agent token。
- 发起短期 acting session，进入任意未归档 workspace 的管理员视角。

server admin token 仍不能直接调用普通 `/api/v1/workspaces`、`/api/v1/members`、`/api/v1/tokens` 等接口。需要进入普通 Console 能力时，必须通过显式的 acting session，且 UI 必须显示“正在以某 workspace 管理员身份操作”的状态。

这样保留两个边界：

- `/api/v1/admin/*` 是 server control-plane API。
- `/api/v1/*` 是 workspace API，只接收普通 PAT / Agent token 或 server 签发的短期 acting token。

### 2.8 Acting session 是短期委托，不是长期 token

“切换到 workspace 管理员身份”不应把 `xuanchu_admin_...` 直接送进普通 API，也不应创建一个长期 Agent token 作为浏览器会话。

推荐模型是 `admin_acting_sessions`：

- 由 server admin token 调用 `/api/v1/admin/workspaces/{workspace}/acting-sessions` 创建。
- 服务端签发一个短期 opaque token，前缀建议 `xuanchu_act_`。
- acting token 只保存在当前浏览器 tab 的 `sessionStorage`，独立于普通用户 token 和 server admin token。
- acting token 绑定一个 workspace、一个实际用户、创建时的 owner/admin role 快照、创建它的 server admin token 和过期时间。
- acting token 只能访问绑定 workspace；project allowlist 默认空，表示该 workspace 内项目按角色权限可见。
- acting token 只面向浏览器 Workspace Console 的普通 HTTP API，不开放给 MCP 或长期自动化使用；remote CLI 必须在客户端侧拒绝 `xuanchu_act_` 前缀，避免用户把浏览器委托误当机器 token。
- 默认 TTL 短，例如 2 小时；刷新页面不恢复 raw token 以外的敏感信息，但 sessionStorage 里的 acting token 在当前 tab 仍可继续使用到过期。
- 用户点击“返回超管界面”时，前端清理 acting token 和 acting metadata，保留 `xuanchu.console.admin_token`，跳回 `/admin/workspaces` 或发起切换的 workspace 详情页。

acting session 必须有可追溯的审计。普通 workspace 操作仍以被切换的用户作为 actor，但 audit / access log 需要额外记录 server admin 来源，例如 `delegator_admin_token_id`、`delegator_admin_token_name` 和 `admin_acting_session_id`。不得出现无法追溯来源的管理员操作。

## 3. 目标

v0.4.1 完成后，应支持以下浏览器流程：

1. 用户打开 `/`。
2. 普通登录页展示 PAT / Agent token 表单，同时提供低调链接进入 `/admin/login`。
3. 用户打开 `/admin/login`。
4. 如果 server 已有有效 admin token，输入 `xuanchu_admin_...`。
5. 如果 server 无有效 admin token，`/admin/login` 显示 setup 引导，提示在 server 控制台查找 setup-code，并跳转 `/admin/setup`。
6. 用户在 `/admin/setup` 输入 setup-code，服务端生成第一个 admin token，raw token 只显示一次。
7. 前端用 admin token 调用 `/api/v1/admin/session` 校验。
8. 校验成功后进入 `/admin`。
9. 在 `/admin` 创建 workspace。
10. 为 workspace 创建或提升 workspace 管理员。
11. 为该管理员创建 workspace-scoped Agent token。
12. raw Agent token 只显示一次，并提示用户保存。
13. 用户进入 `/admin/workspaces` 查看所有 workspace。
14. 用户打开某个 workspace 详情，查看 owner/admin/member 摘要和相关 token 摘要。
15. 用户点击“以管理员身份进入”，选择或确认一个 workspace owner/admin；如果 workspace 暂无 owner/admin，则先创建 owner/admin，再创建短期 acting session 进入普通 Workspace Console。
16. 普通 Console 顶部持续显示 acting banner；用户点击“返回超管界面”后清理 acting session 并回到 `/admin/*`。

v0.4.1 仍不是完整 admin 平台：它只扩展 workspace 控制面和受控切换，不做任务/项目数据的 server-admin 直读 dashboard。

## 4. 非目标

v0.4.1 不做以下内容：

- 不做细粒度 server admin RBAC。
- 不做多个 server admin 角色。
- 不让 server admin token 进入 `api_tokens`。
- 不让 server admin token 拥有普通业务 scope。
- 不让 server admin token 直接读写任务、项目、通知、hook 等 workspace 内业务数据。
- 不做任务/项目/通知/hook 的 server-admin 聚合 dashboard。
- 不做用户搜索中心。
- 不做批量导入。
- 不做 OAuth / OIDC / SSO。
- 不做 cookie session。
- 不做长期保存 raw admin token 或 raw Agent token。
- 不把 acting session 设计成长期 API token。
- 不提供 `/api/v1/admin/*` 之外的 admin 专属业务 API。
- 不通过浏览器 API 返回 setup-code。
- 不让 setup-code 在已有有效 admin token 后继续可用。


### 5.2 Server Admin Console

```text
/admin/login              server admin 登录页
/admin/setup              首次 setup-code 初始化页
/admin                    admin bootstrap 首页，可重定向或链接到 workspace 管理
/admin/workspaces         workspace 管理列表
/admin/workspaces/:workspace
                          workspace 控制面详情
/admin/workspaces/new     创建 workspace
/admin/workspaces/:workspace/admins/new
/admin/workspaces/:workspace/agent-tokens/new
```

这些页面只使用 admin token，数据接口只走 `/api/v1/admin/*`。

`/admin/setup` 不使用 admin token。它只能调用 `GET /api/v1/admin/status` 和 `POST /api/v1/admin/setup`。setup 成功后页面显示 raw admin token 一次，并提示保存；用户确认后再跳转 `/admin/login`。

### 5.3 路由保护

```text
WorkspaceGuardRoute
  token key: xuanchu.console.token
  session API: GET /api/v1/me
  failure: clear workspace token, show normal login

AdminGuardRoute
  token key: xuanchu.console.admin_token
  session API: GET /api/v1/admin/session
  failure: clear admin token, redirect /admin/login

AdminActingGuard / WorkspaceGuardRoute acting mode
  acting token key: xuanchu.console.admin_acting_token
  acting metadata key: xuanchu.console.admin_acting_context
  session API: GET /api/v1/me
  failure: clear acting token, return /admin/workspaces
  return action: clear acting token + acting metadata, keep admin token
```

普通 guard、admin guard、acting mode 不共享长期 token，不共享 session query key，不共享登录表单。acting mode 可以复用普通 Workspace Console 页面，但 token source 必须优先读取 acting token，并在 UI 上持续显示 acting banner。

- 如果 workspace 有 owner/admin，默认选择 owner；也可以让用户在确认 Dialog 里选择具体 owner/admin。

- 创建 acting session 成功后跳转普通 Console，例如 `/workspaces/:workspace/projects` 或 `/`。
- 进入普通 Console 后，顶部显示醒目的 acting banner：`正在以 dajee 的 alice(owner) 身份操作 · 由 server admin ops-primary 委托`，右侧有“返回超管界面”按钮。
- 返回超管界面只清理 acting token，不清理 server admin token。

## 7. 后端 API

### 7.1 Admin 状态 endpoint

```http
GET /api/v1/admin/status
```

该接口匿名访问，只返回控制面状态，不返回 token 数量、hash、setup-code 或配置路径。

成功：

```json
{
  "status": "setup_required",
  "setup_code_expires_at": 1780963621
}
```

`status` 取值：

| status | 说明 |
|---|---|
| `disabled` | `[server.admin].enabled=false`，admin 控制面不可用 |
| `setup_required` | 控制面启用但没有有效 admin token，需要 `/admin/setup` |
| `login_required` | 已有有效 admin token，需要 `/admin/login` |

`setup_code_expires_at` 只在 `setup_required` 且当前进程有有效 setup-code 时返回，用于 UI 提醒过期时间；不返回 code 本身。

### 7.2 Admin setup endpoint

```http
POST /api/v1/admin/setup
Content-Type: application/json

{
  "setup_code": "123456-abcdef",
  "name": "local-admin"
}
```

成功：

```json
{
  "token": "xuanchu_admin_xxx",
  "token_name": "local-admin",
  "prefix": "xuanchu_admin_ab",
  "shown_once": true
}
```

规则：

- 只有 `setup_required` 时可用。
- setup-code 缺失、错误或过期返回 `401 admin_setup_invalid`。
- 已存在有效 admin token 时返回 `409 admin_setup_completed`。
- 生成 token 后写入 `server_admin_tokens` 表，并立即让该 token 可用于 `/api/v1/admin/session`。
- raw admin token 只在该响应中出现一次。
- 操作日志不能记录 setup-code 或 raw admin token。

### 7.3 数据表

新增 `server_admin_tokens`：

| 字段 | 说明 |
|---|---|
| `id` | UUID |
| `name` | token 名称，用于 UI、日志和 audit |
| `token_prefix` | raw token 前缀，便于识别 |
| `token_hash` | `sha256:<hex>` |
| `enabled` | 是否启用 |
| `created_at` | 创建时间 |
| `revoked_at` | 撤销时间，可空 |
| `last_used_at` | 最近使用时间，可空 |
| `description` | 运维备注 |

有效 token 定义：

```text
enabled = true AND revoked_at IS NULL
```

该表不与普通用户、workspace、membership 绑定。它是 server control-plane verifier，不是业务 token。

新增 `admin_acting_sessions`：

| 字段 | 说明 |
|---|---|
| `id` | UUID |
| `token_prefix` | raw acting token 前缀，例如 `xuanchu_act_ab` |
| `token_hash` | `sha256:<hex>`，不保存 raw token |
| `admin_token_id` | 创建该 session 的 `server_admin_tokens.id`，配置文件 admin token 无 ID 时可空 |
| `admin_token_name` | 创建该 session 的 admin token 名称，必须写入，便于审计 |
| `workspace_id` | acting session 绑定的 workspace |
| `actor_user_id` | acting session 实际扮演的用户 |
| `role` | session 创建时确认的角色快照，只允许 `owner` 或 `admin`；审计展示用，不作为后续授权来源 |
| `created_at` | 创建时间 |
| `expires_at` | 过期时间 |
| `revoked_at` | 撤销时间，可空 |
| `last_used_at` | 最近使用时间，可空 |

有效 acting session 定义：

```text
revoked_at IS NULL AND expires_at > now
```

普通 HTTP 鉴权需要先按 token 前缀识别 acting token。如果 token 前缀是 `xuanchu_act_`，只查询 `admin_acting_sessions`，不得落到普通 `api_tokens`。acting session 解析成功后，服务端用 `workspace_id + actor_user_id` 构造普通 API 的 request scope；后续授权必须重新读取该用户在 workspace 内的当前 membership role，而不是信任 session 创建时保存的 role 快照。runtime context 中带上 `AdminActingSessionID`、`DelegatorAdminTokenID`、`DelegatorAdminTokenName`。

### 7.4 复用现有接口

继续复用：

```http
POST /api/v1/admin/workspaces
POST /api/v1/admin/workspaces/{workspace}/agent-tokens
```

`POST /api/v1/admin/workspaces` 已经支持创建 workspace 和初始 owner。wizard 的 Step 1 可以直接调用该接口，并把 `owner` 设置为 Step 2 用户；也可以先创建 workspace，再通过 Step 2 新接口创建管理员。implementation plan 需要在交互上选择更不容易产生重复输入的方式。

推荐交互：

- Step 1 只收 workspace 字段，不调用后端。
- Step 2 收 admin 字段。
- 用户点击 `Create workspace and admin` 时调用 `POST /api/v1/admin/workspaces`，一次创建 workspace 和 owner。
- 如果 workspace 已存在，进入“为已有 workspace 创建管理员”的路径，调用新增 admins endpoint。

这样可以复用现有原子创建语义，同时支持已有 workspace 的管理员补建。

### 7.10 Admin acting session 创建

```http
POST /api/v1/admin/workspaces/{workspace}/acting-sessions
Authorization: Bearer <server-admin-token>
Content-Type: application/json

{
  "user": "alice@example.com",
  "expires_in": "2h"
}
```

成功：

```json
{
  "token": "xuanchu_act_xxx",
  "expires_at": 1780963621,
  "workspace": {
    "id": "workspace-id",
    "slug": "dajee",
    "name": "Dajee"
  },
  "actor": {
    "id": "user-id",
    "name": "alice",
    "email": "alice@example.com",
    "external_ids": []
  },
  "role": "owner",
  "admin_token_name": "ops-primary"
}
```

规则：

- workspace 必须存在且未归档。
- `user` 可选；缺省时选该 workspace 的第一个 owner，再退到第一个 admin。
- 指定用户必须是该 workspace 的 `owner` 或 `admin`，否则返回 `admin_acting_target_invalid`。
- acting token 是短期浏览器会话凭证，不写入普通 `api_tokens`，不出现在普通 token 列表里。
- acting token 只能访问绑定 workspace；普通 API 收到 acting token 时按 `actor` 构造 request scope，并用该 actor 当前 workspace membership role 做权限判断。若 actor 已被降级或移出 workspace，acting token 不应继续拥有原 owner/admin 能力。
- acting token 原文只在创建响应中返回一次。
- 服务端必须能按 token hash 校验 acting token、更新 last_used_at、识别 revoked/expired。
- 普通 HTTP API 可以接受 acting token；HTTP MCP 和 stdio MCP 不接受 acting token。remote CLI client 必须拒绝 `xuanchu_act_` 前缀；如果调用者绕过 CLI 直接构造普通 HTTP 请求，服务端仍按普通 HTTP API 的 acting 规则处理。
- 删除或过期 acting session 后，普通 API 返回 `auth_invalid_token` 或专用 `admin_acting_session_expired`。

可选补充：

```http
DELETE /api/v1/admin/acting-sessions/{sessionID}
```

用于 server admin 主动吊销 acting session。首版可以只依赖短 TTL 和前端清理，但如果实现成本低，建议补齐吊销能力。

## 8. 前端状态与 API 客户端

### 8.1 token storage

```text
xuanchu.console.token          普通 PAT / Agent token
xuanchu.console.admin_token    server admin token
xuanchu.console.admin_acting_token
                              server admin acting session token
xuanchu.console.admin_acting_context
                              acting workspace/user/admin 来源元数据
```

三类 token 必须分开清理、分开校验。普通用户登录/退出不得误清理 server admin token；acting mode 返回超管界面时不得误清理 server admin token；server admin 退出时应同时清理 admin token 和 acting token。

### 8.2 API client

普通 API client：

```text
features/workspace/session
  token source: xuanchu.console.token
  allowed path prefix: /api/v1/
  denied path prefix: /api/v1/admin/
```

Admin API client：

```text
features/admin/session
  token source: xuanchu.console.admin_token
  allowed path prefix: /api/v1/admin/
```

Admin API client 应在前端层面拒绝非 admin path，避免误把 admin token 发到普通业务接口。

Acting workspace API client：

```text
features/workspace/session
  normal token source: xuanchu.console.token
  acting token source: xuanchu.console.admin_acting_token
  acting context source: xuanchu.console.admin_acting_context
```

规则：

- 如果存在有效 acting token，Workspace Console 请求优先使用 acting token。
- acting mode 必须显示固定 banner，说明 workspace、actor、role 和 admin token name。
- “返回超管界面”按钮清理 acting token/context，并导航回 `/admin/workspaces/{workspace}`。
- 普通退出按钮在 acting mode 中应显示为“退出工作区视角”或“返回超管”，避免误以为会退出 server admin。
- 如果 acting token 过期，清理 acting token/context，跳回 `/admin/workspaces` 并显示过期提示。

## 10. 错误语义

| 场景 | HTTP | code |
|---|---:|---|
| admin token 缺失 | 401 | `admin_auth_required` |
| admin token 无效 | 401 | `admin_auth_invalid` |
| admin bootstrap disabled | 404 | `route_not_found` |
| 无有效 admin token | 401 | `admin_setup_required` |

| acting session 已过期 | 401 | `admin_acting_session_expired` |
| token scope 非法 | 400 | `token_scope_invalid` |
| expires_in 非法 | 400 | `admin_token_ttl_invalid` |

前端登录错误统一显示：


不要在未认证页面区分 disabled、invalid、missing。

- 刷新结果页后不再恢复 raw token。
- `/api/v1/*` 不被 SPA fallback 吃掉。
- `/mcp` 不被 Console 拦截。

## 12. 验收标准

v0.4.1 视为完成时必须满足：

1. `/` 是普通登录入口。
2. `/admin/login` 是 server admin 登录入口。
3. 普通登录页没有模式切换。
4. 普通登录页有低调的 admin login 链接。
5. 两个登录页视觉风格明显不同。
6. server admin token 只进入 `/api/v1/admin/*`。
7. 普通 token 只进入普通 `/api/v1/*`。
8. 页面可以创建 workspace。
9. 页面可以创建或提升 workspace 管理员。
10. 页面可以为该管理员创建 Agent token。
11. 页面可以列出所有 workspace 并打开详情。
12. 页面可以从任意未归档 workspace 创建 acting session，进入管理员视角。
13. acting mode 可以返回超管界面，且不丢失 server admin session。
14. raw Agent token 和 raw acting token 只显示一次。
15. 所有新增输出遵守 `UserInfo` JSON 规范。
16. 文档说明 admin token、acting token 与普通 token 的边界。
17. `go test ./...` 通过。
18. `CGO_ENABLED=0 go test ./...` 通过。
19. `CGO_ENABLED=0 go build ./cmd/xuanchu` 通过。
20. `pnpm --dir web test`、`pnpm --dir web typecheck`、`pnpm --dir web build` 通过。
21. `git diff --check` 通过。

## 13. 后续非 v0.4.1 候选

这些能力不进入 v0.4.1，但可以作为后续版本：

- server admin token verifier 列表和轮换 UI。
- admin bootstrap 操作历史页。
- 多 admin 角色。
- SSO / OIDC。
- cookie session。
- workspace 初始化模板。
- 为 Agent 平台生成预设项目、通知 sink、hook 规则。
