# v0.1.1 设计文档：稳定短任务标识 task_slug

日期：2026-06-07

> **给 agentic workers 的要求：** 编码前必须先使用 `superpowers:writing-plans` 将本文档拆成实施计划。不要直接从本规格开始写代码。

## 1. 背景

Xuanchu v0.1.0 已完成本地 CLI、远程 CLI、HTTP API、MCP Server、Hook、Agent Token、多数据库和基础运维能力。当前任务的稳定身份仍以 UUID 为主，人类日常操作则依赖列表里的数字 working-set ID。

这两类标识各有问题：

- UUID 稳定但太长，不适合人和 Agent 在对话、项目群、会议纪要中快速引用。
- 数字 working-set ID 短，但只表达当前默认 working set 的位置，不是持久身份。

v0.1.1 需要新增一种稳定、短、可读的任务引用：`task_slug`，格式为 `<projectSlug>-<seq>`。它应服务企业项目协作和 Agent MCP 场景，让任务可以被引用为 `api-1`、`qa9-42` 这类短字符串，同时保留 UUID 作为底层稳定身份。

当前项目尚未正式上线，不需要兼容旧生产数据。测试库可以清除或按新规则重建。因此 v0.1.1 可以直接收紧现有 `project.slug` 规则，不为旧的 `ai-agent-platform`、`web-app` 等带连字符 slug 做兼容迁移。

## 2. 目标

- 收紧 `project.slug`，使其可以安全作为 `task_slug` 前缀。
- 为每个 project 分配独立递增的任务序号。
- 在所有 task JSON 输出中新增 `task_slug` 字段。
- human `list` / `info` 输出展示短任务标识。
- task ref / target 解析按入口分层支持：
  - 本地 CLI：纯数字 working-set ID、UUID、`task_slug`
  - 远程 CLI：纯数字 working-set ID 由客户端两跳解析；UUID、`task_slug` 直接传给服务端
  - HTTP API：只接受 UUID、`task_slug`，不接受纯数字 working-set ID
  - MCP tool：只接受 UUID、`task_slug`，不接受纯数字 working-set ID
- CLI、远程 CLI、HTTP API、MCP tool 共用同一 app service 解析核心，但通过 resolver mode 明确是否允许数字 working-set ID。
- 保持 workspace/project 隔离：`task_slug` 只在 effective workspace 内解析，不做跨 workspace 搜索。

## 3. 非目标

- 不引入第二套 project short slug。现有 `project.slug` 就是 `task_slug` 的前缀来源。
- 不保留旧 project slug 格式兼容。
- 不支持 project slug rename。
- 不支持 task slug alias 历史表。任务移动 project 后旧 slug 立即失效。
- 不让用户手工指定或修改 `project_seq`。
- 不把 `task_slug` 作为数据库持久字段；它是由 `project.slug + task.project_seq` 派生出的输出字段。
- 不替换 UUID。UUID 仍是内部稳定身份、外部系统长期集成和 audit target 的主要底层 ID。

## 4. 核心产品决策

### 4.1 projectSlug 规则

`project.slug` 输入允许大小写英文和数字，存储和输出统一转小写。规范化后必须匹配：

```text
^[a-z][a-z0-9]{2,9}$
```

规则含义：

- 只允许英文字母和数字。
- 不能以数字开头。
- 长度至少 3 位。
- 长度至多 10 位。
- 输入 `API`、`Api`、`api` 都归一为 `api`。
- 同一 workspace 内不能重复。
- 不同 workspace 可以重复。

示例：

| 输入 | 规范化 | 结果 |
|---|---|---|
| `api` | `api` | 合法 |
| `API9` | `api9` | 合法 |
| `p1` | `p1` | 非法，长度不足 3 |
| `1api` | `1api` | 非法，数字开头 |
| `web-app` | `web-app` | 非法，包含 `-` |
| `ai_agent` | `ai_agent` | 非法，包含 `_` |
| `verylongslug` | `verylongslug` | 非法，超过 10 位 |

### 4.2 task seq 与 task_slug

每个 project 拥有自己的任务序号计数器：

- `projects.next_task_seq` 从 `1` 开始。
- `tasks.project_seq` 表示该任务在当前 project 下分配到的序号。
- `tasks.project_seq` 可空；没有绑定 project 的任务没有 `task_slug`。
- 创建绑定 project 的任务时分配当前 `next_task_seq`，然后递增 project counter。
- `task_slug = <project.slug>-<tasks.project_seq>`。

示例：

```bash
xuanchu project add api name:API
xuanchu add "Design endpoint" project:api
xuanchu add "Write tests" project:api
```

输出中的短标识分别为：

```text
api-1
api-2
```

### 4.3 seq 不回收

`project_seq` 不回收。

如果任务完成、删除、移动到其它 project，原 project 的序号都不再复用。这样可以避免同一 project 内短 ID 在不同时间指向不同任务，降低审计、聊天记录和 Agent 对话中的误引用风险。

### 4.4 任务移动 project

任务移动 project 时：

- 从 project A 移动到 project B：分配 project B 的下一个 seq，旧的 `a-N` 立即失效。
- 清空 project：清空 `project_id`、`project` 和 `project_seq`，任务不再有 `task_slug`。
- 从无 project 移动到 project B：分配 project B 的下一个 seq。
- 修改其它字段但 project 不变：保留原 `project_seq`。

这意味着 `task_slug` 是稳定短引用，但稳定范围是“任务当前 project 归属不变时”。UUID 仍是跨 project 移动后的长期稳定身份。

## 5. 数据模型

### 5.1 projects

新增字段：

```text
next_task_seq INTEGER NOT NULL DEFAULT 1
```

约束：

- 创建 project 时 `next_task_seq = 1`。
- 分配任务序号必须在事务内更新该字段。
- `next_task_seq` 不因任务删除或移动而回退。

### 5.2 tasks

新增字段：

```text
project_seq INTEGER NULL
```

约束：

- `project_seq` 只在 `project_id` 非空时有值。
- `project_id` 为空时 `project_seq` 必须为空。
- 同一 workspace + project 内 `project_seq` 唯一。

建议索引：

```text
UNIQUE(workspace_id, project_id, project_seq)
INDEX(workspace_id, project_id, project_seq)
```

SQLite 对 `NULL` 的 unique 语义允许多条无 project 任务，因此无 project 任务不会互相冲突。PostgreSQL 行为也符合这个需求。

### 5.3 派生字段

不新增数据库字段 `task_slug`。输出时按以下规则派生：

```go
if task.Project != nil && task.ProjectSeq != nil {
    taskSlug = fmt.Sprintf("%s-%d", *task.Project, *task.ProjectSeq)
}
```

如果发现 `project_id` 非空但 `project` 或 `project_seq` 缺失，应视为数据不变量损坏，返回稳定错误，不静默输出错误 slug。

## 6. App Service 设计

### 6.1 序号分配

新增 app/storage 能力，但它不能作为“先分配、后写任务”的独立外部步骤使用。序号分配必须嵌入创建任务、移动 project、创建 recurring child 的同一个事务。

推荐 storage contract：

```go
WithProjectTaskSeq(workspaceID, projectID string, fn func(seq int64) error) error
```

推荐实现方式：

- SQLite：在同一个写事务内读取 project 当前 `next_task_seq`，更新为 `next_task_seq + 1`，再由回调写入 task。
- PostgreSQL：使用 row lock（如 `SELECT ... FOR UPDATE`）或原子 `UPDATE ... RETURNING` 等等效方式完成“锁定 project counter -> 取 seq -> 更新 counter -> 写 task”。
- 如果回调失败，整个事务回滚，counter 不递增，避免写任务失败却消耗 seq。
- 任务创建、任务移动 project、recurring child 创建必须通过这类事务性方法完成。
- 数据库唯一索引作为兜底，不作为主要分配机制。
- 测试必须覆盖并发创建同一 project 下多条任务时不会分配重复 seq。

### 6.2 创建任务

`Add` / `AddWithAnnotations` / recurring child 创建路径都必须遵守：

- 有 project：解析 active project 后分配 `project_seq`。
- 无 project：`project_seq = nil`。
- recurring child 继承 parent project 时，分配该 project 的新 seq，而不是复用 parent 或 previous child 的 seq。

### 6.3 修改任务

`Modify` / `ReplaceEditableTask` / import update 路径都必须遵守：

- project 不变：保留原 `project_seq`。
- project 变更为另一个 active project：分配新 project 的下一个 seq。
- project 清空：清空 `project_seq`。
- 不允许用户直接编辑 `project_seq` 或 `task_slug`。

### 6.4 解析任务引用

App 层提供统一解析入口，例如：

```go
ResolveTaskRef(target string, mode ResolveMode) (task.Task, error)
```

resolver mode：

| Mode | 用途 | 支持数字 working-set ID |
|---|---|---|
| `ResolveInteractive` | 本地 CLI、人类交互命令、远程 CLI 客户端本地两跳解析 | 是 |
| `ResolveProtocol` | HTTP API、MCP tool、远程服务端 | 否 |

`ResolveInteractive` 解析顺序：

1. 纯数字且 `>= 1`：按默认 working set ID 解析。
2. UUID：按 UUID 解析。
3. `task_slug`：按 `<projectSlug>-<seq>` 解析。

`ResolveProtocol` 解析顺序：

1. UUID：按 UUID 解析。
2. `task_slug`：按 `<projectSlug>-<seq>` 解析。
3. 纯数字：返回 `task_ref_invalid`，不按 working set ID 解析。

`task_slug` 解析规则：

- 使用最后一个 `-` 切分，右侧必须是正整数。
- 左侧按 project slug 规则规范化为小写并校验。
- 在 effective workspace 内解析 project。
- 用 `(workspace_id, project_id, project_seq)` 找 task。
- 找不到时返回 `task_not_found`。
- token project scope / 权限校验仍按解析出来的 task 执行。

因为新 project slug 不允许 `-`，`api-12` 的切分没有歧义。

## 7. CLI 行为

### 7.1 创建和输出

创建任务后 human 输出继续保持简短，可以保留现有文案；`--json` 输出必须包含 `task_slug`。

`list` 表格新增 `SLUG` 列，建议列顺序：

```text
ID  SLUG  UUID  PRI  PROJECT  ASSIGNEES  TAGS  DESCRIPTION
```

无 project 任务的 `SLUG` 显示为 `-`。

`info` 输出新增：

```text
Task slug: api-1
```

无 project 任务显示为空或不显示均可。为保持表格字段稳定，建议显示为空。

### 7.2 target/action

以下命令都应接受 `task_slug`：

```bash
xuanchu info api-1
xuanchu api-1 modify priority:H
xuanchu api-1 done
xuanchu api-1 delete
xuanchu api-1 annotate "note"
xuanchu api-1 link add ...
xuanchu _get api-1.uuid api-1.description
xuanchu urgency api-1
```

纯数字 working-set ID 和 UUID 行为保持不变。

### 7.3 project 命令

`project add` 使用新 slug 规则。

示例需要从旧风格：

```bash
xuanchu project add ai-agent-platform name:"AI Agent Platform"
```

改为：

```bash
xuanchu project add api name:"API"
```

`project info/modify/archive` 继续接受 slug 或 project UUID。slug 统一按新规则规范化。

## 8. JSON / HTTP / Remote / MCP

### 8.1 JSON 字段

`task.JSONTask` 新增：

```json
{
  "task_slug": "api-1"
}
```

规则：

- 有 project 且有 `project_seq` 时输出字符串，例如 `"task_slug": "api-1"`。
- 无 project 时省略 `task_slug` 字段，延续现有 optional JSON 字段的 `omitempty` 风格。
- `task_slug` 是只读保留字段，不作为 import/edit 的权威输入。
- `project_seq` 也是只读保留字段，不进入公开 JSON 输出。
- import/export round-trip 中可能出现 `task_slug`，导入和编辑应接受该字段但忽略其值，避免把派生输出字段误当作权威输入。
- import/edit JSON 中出现 `project_seq` 必须拒绝，不允许进入 UDA / orphan UDA。错误应稳定，提示通过 `project:<slug>` 修改 project，而不是直接编辑派生序号。
- 所有复用 `task.JSONTask` 的输出都使用同一规则，包括 CLI `--json`、HTTP API、MCP data、remote CLI 反序列化、export 和 Hook task payload。

### 8.2 HTTP API

HTTP task path 从语义上升级为 `{taskRef}`：

```text
GET    /api/v1/tasks/{taskRef}
PATCH  /api/v1/tasks/{taskRef}
DELETE /api/v1/tasks/{taskRef}
POST   /api/v1/tasks/{taskRef}/done
POST   /api/v1/tasks/{taskRef}/start
POST   /api/v1/tasks/{taskRef}/stop
```

兼容行为：

- UUID 继续可用。
- `task_slug` 新增可用。
- 纯数字 working-set ID 不支持。HTTP 是无状态协议，working-set ID 依赖默认 working set，不适合作为服务端 path 标识。远程 CLI 如果用户输入纯数字，仍由客户端通过 list 两跳解析。

HTTP 错误码：

- 格式非法：`task_ref_invalid`
- 格式合法但找不到：`task_not_found`
- token scope 不允许：沿用现有 `task_not_found` 或 `project_scope_denied` 的隐藏策略，不因 task_slug 泄露资源存在性。

### 8.3 Remote CLI

远程 CLI target 解析更新为：

- UUID：如果带 project scope，需要确认该 UUID 在 scope 内；否则直接调用 HTTP。
- 纯数字：继续通过远程默认 working set 两跳解析为 UUID 或 task_slug。
- `task_slug`：可直接传给 HTTP `{taskRef}`；如果带 project scope，服务端仍会校验 scope。
- UUID 前缀：保留当前通过 working set 匹配 UUID 前缀的行为，但不扩展为 task_slug 前缀匹配，避免 `api-1` / `api-10` 歧义。

### 8.4 MCP

所有 task tool 的 `id` / `task` 字段描述改为：

```text
task reference: UUID or task_slug
```

实现上不应在 tool handler 里先 `requireUUID`，而应调用 app service 的统一 task ref 解析。涉及范围至少包括：

- `task_get`
- `task_modify`
- `task_done`
- `task_delete`
- `task_start`
- `task_stop`
- `task_annotate`
- `task_denotate`
- `task_depends`
- `task_link_add`
- `task_link_remove`
- `task_link_list`

MCP 返回的 task data 使用同一个 `task.JSONTask`，因此自动包含 `task_slug`。

MCP tool 不支持纯数字 working-set ID。M15 已要求 Agent 每次显式传 workspace/project，不依赖隐式 context；数字 working-set ID 属于 CLI 交互体验，不进入 MCP 协议契约。

## 9. 权限与隔离

- `task_slug` 只在 effective workspace 内解析。
- 不同 workspace 可以同时存在 `api-1`。
- token scoped 到单 workspace 时，只能解析该 workspace 内的 `api-1`。
- token scoped 到 project allowlist 时，解析出 task 后必须继续执行 `ensureReadableTaskScope` / `ensureWritableTaskScope`。
- 如果 task 存在但不在 token project allowlist 内，仍按现有隐藏策略返回 `task_not_found`，避免通过短 ID 探测资源存在性。

## 10. 迁移策略

项目未上线，不要求旧数据兼容。v0.1.1 的迁移策略按“测试库可清除”处理，但实现仍需要对打开旧 schema 的行为给出确定结果。

- 新库直接创建 `projects.next_task_seq` 和 `tasks.project_seq`。
- 旧测试库可以删除重建，这是推荐开发路径。
- 如果打开旧 schema，迁移必须执行确定策略：
  - 为 `projects` 增加 `next_task_seq`，默认值为 `1`。
  - 为 `tasks` 增加 `project_seq`。
  - 所有既有 `projects.slug` 必须符合新规则；不符合时迁移失败，返回稳定错误 `project_slug_migration_required`，提示清理或重建数据库。
  - 对符合新规则且已有 project 的旧任务，按 `(workspace_id, project_id, entry ASC, uuid ASC)` 确定性回填 `project_seq`。
  - 每个 project 的 `next_task_seq` 回填为 `max(project_seq) + 1`。
  - 不对旧 slug 自动改名，不生成兼容 alias。
- SQLite 和 PostgreSQL 都必须覆盖新 schema；SQLite 的旧库迁移至少覆盖“合法旧 slug 可回填”和“不合法旧 slug 稳定失败”两个路径。

## 11. 测试要求

### 11.1 单元测试

- `normalizeProjectSlug`：
  - 接受大小写输入并转小写。
  - 拒绝数字开头。
  - 拒绝长度小于 3 或大于 10。
  - 拒绝 `-`、`_`、非 ASCII 字符和空白。
- task slug 派生：
  - 有 project + seq 输出 `task_slug`。
  - 无 project 不输出或输出空值，按最终 JSON 策略固定测试。
- task ref 解析：
  - 数字 working-set ID。
  - UUID。
  - `task_slug`。
  - 跨 workspace 同名 slug 不串数据。
  - project scope denied 不泄露。
- 序号分配：
  - 同 project 从 1 开始递增。
  - 不同 project 各自从 1 开始。
  - 删除或完成不回收。
  - 移动 project 后分配新 seq，旧 slug 失效。
  - recurring child 获取新 seq。
  - 并发创建同一 project 下多条任务不会分配重复 seq。
